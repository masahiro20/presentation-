# 図面の読み取り方式の比較（2026-11-19）

| 方式 | 強み | 弱み | 今回の判断 |
|---|---|---|---|
| A ベクター解析（PDF の線・塗り・文字を直接読む） | 座標と寸法が正確（mm 単位で 0.01㎡ まで面積表と一致）。同じ図面なら毎回同じ結果。原因を特定してルールで直せる | 描き方が想定と違うと崩れる（実施図の多重線、画像で貼られた図面） | **主軸として維持**。今回の改善もここ（壁の最小厚み・図面枠とのつながり・階段の形） |
| B 画像認識 | 画像で貼られた図面・スキャンにも使える | 寸法の精度が落ちる。学習データ（正解つきの図面）が要る | 既存の「画像から太線を拾う」経路のまま。正解データが 1 件しか無い今は、学習型は導入しない |
| C OCR | 画像の図面の文字を読める | PDF に文字が入っていれば不要。誤読がある | PDF の文字を優先（方針どおり）。画像の図面の室名・帖数に限って今後検討 |
| D AI（マルチモーダル）による図面理解 | 建具記号・部屋の用途・階段の形など「意味」の判断に強い | 有料 API・図面の外部送信が要る（今回の方針で事前確認が必要）。結果が毎回同じとは限らず、寸法は不正確 | **今回は使わない**。既存の「AI 設計士の確認」は任意のまま。使う場合も「らしい」では確定せず、修正案（B）として出す |
| E ハイブリッド（A＋建築ルール＋必要な所だけ B〜D） | A の正確さに、建築の成立条件での検算と自動修正を足せる | 組み立てが複雑 | **採用**。今回は A＋建築ルール（階段の寸法・半間単位・上下階の対応）で、誤認識の原因の切り分けと自動修正を入れた |

## 新しいライブラリ
今回は導入していない（既存の pdf.js・three.js と自前の幾何演算だけで実装）。
AI・画像認識は、正解データ（設計担当者が確認した間取り）が 20 件ほど集まってから、精度・速度・費用を実測して判断する。
